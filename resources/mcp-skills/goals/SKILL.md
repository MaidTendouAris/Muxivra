# 需求与选型

用户无需知道编码术语。先判断媒体类型、用途和首要目标，再用普通语言说明方案、代价和保留内容。已有明确格式、画面、音轨或设备要求时优先遵守；单一模糊偏好通常可按以下默认策略推进，不能把它解释为可以改变分辨率、删轨道、裁剪内容或覆盖原文件。

## 将用户表达转成处理目标

| 用户表达 | 优先方案 | 应向用户说明的取舍 |
| --- | --- | --- |
| “快一点”“尽快处理”“别占 CPU” | 必须重编码时优先当前设备可用的硬件编码器：NVIDIA NVENC、Intel QSV、AMD AMF；无需重编码的兼容封装/提取用 copy | 同等视觉质量下体积可能更大；滤镜、解码、磁盘仍可能限速，GPU 加速不能保证倍数 |
| “压缩率高”“文件尽量小”“节省空间” | 目标播放器支持时优先 H.265 / HEVC 或 AV1；兼顾速度选可用硬件，容许更久时考虑 libx265 / libsvtav1 软件编码 | 兼容性和耗时需要取舍；不是任何源文件都会变小，不承诺固定压缩比例 |
| “画质好”“尽量清晰”“不要糊” | 保留原始尺寸、帧率、色彩特征；使用质量控制，适当提高质量并考虑较慢的编码速度预设 | 通常增加文件体积或时间；有损重编码不能恢复源中已经丢失的细节 |
| “完全无损”“只换格式/封装” | 容器兼容且不改画面/声音时复制轨道；确需重编码时先确认数学无损还是视觉无损 | copy 保持压缩数据但不提高压缩率；“看不出差别”与数学无损不同，文件可能更大 |
| “通用”“老设备也能播”“发给别人” | 通常选 MP4 + H.264 + AAC；特殊播放设备按其明确限制选 profile、像素格式和尺寸 | H.265/AV1 兼容性需核对，不能只因压缩率高就替换用户指定的 H.264 |
| “小于 100 MB”等硬体积限制 | 从保留时长和总预算估算码率，扣除音频和封装开销；使用码率模式 | CRF/CQ 不保证最终体积；码率太低会损害画质，不能用文件上限截断内容冒充完整压缩 |
| “听起来好”“音乐无损” | 音频走 audio 指南：无损源可 FLAC/复制；兼容的有损输出可 AAC M4A，质量由音频编码参数控制 | GPU 视频编码器不加速 AAC/MP3；有损音乐转 FLAC 不会恢复细节，提高码率也不能修复原始损失 |

用户同时要求“最快、最小、完全无损”或目标设备限制与格式冲突时，说明具体冲突，只问决定方案所必需的问题，例如“更优先速度还是文件大小？”不要一口气要求用户提供所有专业参数。“画质好”也不自动代表要超分、锐化、插帧或 HDR 转 SDR。

## 能力确认与选型顺序

1. inspect_media 确认轨道、源编码、时长、尺寸、色彩信息；get_system_hardware 和 get_engine_capabilities 确认设备与引擎。available/missing/error 和 not-tested 状态必须保留。不要按厂商品牌猜具体代际是否支持 AV1 编码，也不要把解码能力当作编码能力。
2. 选定编码器必须存在于当前 engine.encoders。硬件型号匹配只是候选，不代表驱动、会话、像素格式或该编码能实际运行。get_component_capabilities 查询真实选项、预设及范围；必要时在用户授权处理的范围内说明并进行一个短片段试编码，成功后再用于批量任务。仅要求计划/连接时不执行试编码。测试输出采用独立名称，原文件保留。
3. 硬件失败先报告实际错误。满足同一目标的替代编码可提出，但改用明显更慢的软件编码、改变输出格式或降低质量之前，说明影响并向用户确认；不要在批量任务中不断重复失败的硬件参数。
4. 从 list_presets 获取完整 options；改编码器时清除旧 presetId、无关的 codecParameters / encoderOptions，保留用户要求的轨道、尺寸与滤镜。内置 h264-1080 预设含 1080 高度上限；用户要保留 4K 时删除 maxHeight，不能直接套用。
5. 使用 parameters 指南的结构化字段，再调用 plan_transcode 检查警告和轨道。计划校验通过仅代表参数合法，不代表硬件已经跑通，也不代表输出质量或体积已达到目标。

## 质量、速度与码率怎样落到参数

- 本应用 options.advanced.rateControl = auto 会按编码器选择质量参数：libx264/libx265/libsvtav1 等用 CRF，NVENC 用 CQ，QSV 用 global_quality，AMF 用 CQP。不要对所有硬件统一强制 crf，也不要叠加互相冲突的质量和码率参数。
- quality 的范围与方向以实际编码器为准。对本指南中的 CRF/CQ/QP 等，较小值一般表示更高质量，但不同编码器、不同模式的数值不等价。内置 H.264 CRF 22、H.265 CRF 26 是起点，不是相同质量的证明。不能将“90% 画质”直接写成 quality = 90。
- options.speed 是编码速度预设，不是播放倍速。本应用对 libsvtav1 的 fast/medium/slow 映射为 10/8/4，对 NVENC 映射为 p2/p4/p6；也接受引擎实际支持的对应预设名称或数值。x264/x265 使用实际支持的 fast/medium/slow 等，不能跨编码器照搬。
- 速度优先可从硬件 + fast 开始，画质/压缩效率优先可从合适的质量值 + medium/slow 开始。更快的 preset 不等于必然降低观感，但常需更大码率；更慢也不会凭空提升损坏的源。先说明方案，质量敏感时用有代表性的片段比较暗部、运动、文字及颗粒，按结果调整，不承诺某个固定值适合全部内容。
- 目标体积估算：总码率 kbps ≈ 目标字节数 × 8 / 时长秒 / 1000；减去所有保留音轨的码率，再留封装余量。使用 advanced.rateControl = bitrate 和 advanced.videoBitrate（kbps），必要时使用引擎支持的码率约束。advanced.fileSize 是终止输出的上限，可能截断文件，不能当作完整视频的定体积方案。本应用没有自动两遍编码流程，不能承诺精确文件大小；完成后核对实际体积并报告偏差。
- 不自动降分辨率/帧率或音频采样率/声道来实现“更小”，也不自动去噪、改色、删字幕。HDR/10-bit 输入在重编码时需明确保留兼容的位深/色彩参数，或先询问转换要求；默认 yuv420p 不等于保留 HDR。
- 增大队列并发不保证单任务更快，可能争用显存、编码会话、CPU 或磁盘。不要为“快一点”擅改全局设置。

## 应答与结果

方案可这样说明：“优先用本机可用的 HEVC 硬件编码，保留原尺寸和帧率，音轨按兼容情况保留；速度优先，但最终大小要看内容。先检查实际能力和处理计划。”这是一种表达示例，不能跳过用户的明确要求。

提交后按 workflow 查询最终状态、耗时和输出大小；体积收益用实际输入/输出大小计算，速度用真实执行数据，预计剩余时间应说明是估计。输出再次 inspect_media 需要该路径也属于用户授权的媒体目录；默认输出授权只赋予输出用途，不自动变成输入授权。

选型原则由项目实现、[FFmpeg 编码文档](https://ffmpeg.org/ffmpeg-codecs.html)、[FFmpeg 轨道复制说明](https://ffmpeg.org/ffmpeg.html#Streamcopy)、[NVIDIA FFmpeg 加速说明](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/ffmpeg-with-nvidia-gpu/index.html)核对，日期 2026-10-11。这些链接是维护来源，执行任务无需实时联网；实际支持项以本机工具响应为准。
